**Enforcement: required.** Work that is not authorized here does not start. The offline documentation checks require queued proposal documents, explicit
agent model assignments and matching detailed-proposal metadata;
`marketing-crosswalk validate` fails on status drift — the rest is on the author and the owner.

Every architecture, module, or process change enters this queue before implementation. Nothing
skips the queue; nothing in `Deferred` is worked without being re-accepted here first.

Proposals too large for a row plus an inline detail section get their own file under
[`proposals/`](proposals/), written from [`proposals/TEMPLATE_PROPOSAL.md`](proposals/TEMPLATE_PROPOSAL.md)
and linked from the row. **A proposal document that no row points at is not queued work**, however
well argued it is.

How to write one that will be accepted: [`PROPOSAL_CREATION_SOP.md`](PROPOSAL_CREATION_SOP.md).
That doc owns *form and evidence*; this file owns *state*.

What is **waiting on a person** — owner decisions and live runs — is indexed by lane in
[`todo/README.md`](todo/README.md). That index is derived from this queue and never authorizes
anything; when it disagrees with a row here, this file wins.

## Agent model selection

**Required for every proposal item.** Set the **best available model for the actual work**,
its exact model ID, reasoning effort and a short scope-based rationale in the row's
**Agent model / effort** column before implementation starts. Select that model and effort in
Codex's execution controls; a Markdown assignment does not configure the running task.
Confirm the selected model and effort are available in the execution client. If they are
unavailable, record an available replacement and its rationale before proceeding; preserve the
capability needed by the work. Reassess the assignment when scope or available models change.

These are development-agent assignments. Runtime Ollama, ComfyUI, CV and TTS model choices
remain in their module configs/proposals. Completed rows record today's recommendation for
follow-up work, not the model that performed historical work. Assigning a model does not accept
Pending or Deferred work or replace owner, hardware, account or release decisions.

**Selection reviewed: 2026-10-04.** These models are exposed by this Codex host. The role choices
follow [official Codex model guidance](https://developers.openai.com/codex/models) and
[OpenAI model selection guidance](https://developers.openai.com/api/docs/guides/model-selection);
individual assignments and efforts are repository judgments, not measured per-proposal rankings.

**Default to `gpt-6.1-sol` for coding and implementation**, including native, security and cross-app
work with clear contracts and meaningful checks. Official Codex guidance recommends it for complex
coding and describes near-Astra performance at lower cost. Astra remains the most capable overall;
reserve it for the hardest coupled architecture/integration work, difficult review, or an explicit
escalation when Sol does not meet the acceptance bar. Native paths or security-sensitive scope alone
do not establish that Astra will perform better. Compare outcomes on representative work when
deciding to escalate, rather than assuming the model family proves correctness.

|---|---|---|

## Adding a proposal

1. Take the next free number. Numbers are permanent — a retired proposal keeps its number and
   moves to `Done` or `Deferred` with a reason, it is not reused.
2. Small enough for a row plus an inline `### P-0NN detail` section? Do that. Otherwise write a
   file under `proposals/` from the template and link it.
3. **Set the best available agent model, reasoning effort and rationale** using
   [the selection policy](#agent-model-selection), then copy the assignment into the detailed
   proposal header. Check the execution client supports it before starting.
4. State starts at `Pending`. Only the owner moves it to `Accepted`, in a change to this file.
5. **Verify locally before moving it to `Done`.** Look up what proves your change in
   [`agent/VERIFICATION-MATRIX.md`](agent/VERIFICATION-MATRIX.md), run it, and record the result
   in the row — which command, what it returned. "Tested" is not a verification. If something
   could not be run, say so and why; **"not run" is acceptable, silence is not.**
6. When it reaches `Done`, `DM-PROPOSAL-DONE` ([`agent/DOC-UPDATE-MATRIX.md`](agent/DOC-UPDATE-MATRIX.md))
   requires the doc named in the row to actually hold the decision — the queue keeps only state.
